# 游戏修改器开发

把目标功能推进到有证据的实现。先判定目标是读信息、显示信息、改数据、改行为还是文件/引擎 Mod，再选择工具。读取成功、定位成功、模型通过和实际游戏生效分别报告。

## 入口与按需资料

| 输入 | 首个产出 | 按需读取 |
|---|---|---|
| 只有游戏和目标功能 | 技术分类与可观察实验 | `references/engine-routes.md` |
| 原版工具、CE 表、程序集 | 样本身份与功能调用链 | `references/skyeye-case-study.md` |
| 现有源码与构建入口 | 可重现构建与最小功能切片 | `references/engineering.md` |
| 更新后失效 | 旧新 build 差异与定位恢复证据 | `references/engineering.md` |
| 没有运行中的游戏 | 静态成果与可控第二案例 | `references/fixture-lab.md` |
| 选择外部技能和工具 | 依赖与能力缺口 | `references/ecosystem.md` |

只加载当前路线需要的资料。模板见 `assets/investigation-template.md`。这些资料包含方法，不把 CoH3 的偏移移植到其他游戏。

## 1. 固定输入身份与约束

1. 读取工作区规则，识别冻结原版、开发区和交付区。在本仓库遵守 `<Game>/original`、`dev/<方向>`、`output/<方向>`，original 只读；分析输出和构建缓存写入开发区。
2. 列出用户给的游戏、工具、表、源码和日志。记录路径、大小、SHA256、架构、PE/CLR 及版本；游戏版本和参考工具版本分别记录。声明每项结论针对哪个文件。
3. 把一句目标改成可观察契约：何时触发、预期变化、如何复位、如何排除假阳性。例如生命值必须随受控受伤变化，不能以某个等值数字作为唯一证据。
4. 盘点已暴露 MCP、CLI、SDK 和工具版本。先使用任务匹配工具；列出实测可用能力与缺项。静态成功不代表动态附加可用，工具安装不代表 MCP 已连接。
5. 不启动不明参考工具来代替分析。优先静态检查；若需要运行，记录隔离环境和可复现启动方式。研究范围跟随用户给定游戏与材料，不读取无关账户、凭据或私钥。

完成条件：样本身份、目标契约、工作目录和能力清单足以复现调查。

## 2. 选择路线并追踪机制

读取 `references/engine-routes.md`，用实际文件/模块/元数据识别 native、Mono、IL2CPP 或 Unreal，目录名仅是线索。

- **参考工具**：沿 UI/热键 → 状态门控 → 功能调度 → 地址解析 → 读写/渲染 API 追踪。区分内嵌资源、托管依赖、原生导入、混淆和业务逻辑；保留原始和派生工件。反编译源码先核对类型/方法与样本身份，再用它解释原版。
- **从零定位**：选择可控变化，保存前后读数及时间，逐步排除候选；找对象归属、字段类型和访问逻辑，继续寻找跨启动稳定根。
- **功能分类**：外部读内存/覆盖层、外部写字段、代码补丁、进程内扩展、文件数据 Mod 各自立项。Window topmost 的 restore 不能充当游戏代码恢复证据。
- **原版受封装或混淆影响**：先判断托管元数据是否仍可读取、资源是否内嵌、是否有转发或动态加载层；只对观测到的层选择解包/恢复工具。记录工具输出与重新核对结果，避免凭文件名宣称已脱壳。

原版商业授权、你自己的产品授权、游戏功能定位是三种独立机制。分析时分别建调用链；交付自己的工程优先使用可维护实现与已有授权接口。

完成条件：至少一条与目标直接相关的机制链，每个关键节点有地址、源码位置、工具输出或运行观察。

## 3. 验证地址而非背诵偏移

1. 用模块相对 RVA、对象路径、指针链、引擎元数据或 AOB 表达定位。保留 ASLR 模块基址和每级解引用过程；标注 32/64 位指针和字段类型。
2. 每次读校验区域、权限、长度、溢出、空指针和实际返回字节数。对对象加入多个独立不变量，例如类型标记、数量界限、关联字段和时间变化。
3. 缓存命中也要复验。按 PID、启动时间、模块身份、对局/场景 epoch 绑定状态；切局、重连、退出时取消旧扫描和旧对象。
4. AOB 遮蔽重定位和可变操作数，保留有区分力的上下文。0 命中视为失配；多命中继续验证候选，不能选首个。唯一命中后仍要解码目标、验证预期指令/结构与行为。
5. 对扫描设置可配置时间、区域和字节预算。先提示/结构路径，后区域扫描；记录覆盖范围，不能以扫描中止推断对象不存在。
6. 至少两次新进程验证跨启动根，再覆盖场景/存读档变化。版本更新必须重新验证；旧 build 的偏移只属于旧 build。

完成条件：排除一个真实歧义来源，并在声明的验证环境重复定位；仅静态时列出动态待办。

## 4. 实现一个最小功能切片

读取 `references/engineering.md`。沿“采集 → 验证 → 数据模型 → 功能 → UI”拆分；先让一个功能完成正确的开启、关闭与退出，再扩展。

- 读取与覆盖层：保持只读句柄；采集线程产出一致快照；验证相机/坐标、DPI、多显示器与窗口模式；没有有效快照就隐藏过期标记。
- 字段写入：限定已确认字段、类型和触发条件；需要维持写入时使用有节流且可取消的循环。记录操作前值及游戏随后更新该值的语义，避免关闭功能时盲写过期状态。
- 指令补丁：核验目标 build 与原始字节、完整指令边界、分支范围和 x64 ABI。记录预期原字节、实际安装字节和资源所有权；关闭时只有当前字节仍是自己的补丁才恢复，冲突时保留现场并停止操作。线程仍执行 trampoline 时不得释放其内存。
- UI 独立于底层状态机；失配、读取失败和进程退出产生可诊断状态。工具缺项时实现离线验证和可交接适配接口，明确运行验证缺口。

## 5. 验证阶梯

每项测试保存命令、输入身份、预期、实际、退出码和工件路径。缺项记 `not_run`，不要冒充通过。

| 等级 | 验证内容 | 能支持的结论 |
|---|---|---|
| S 静态 | 文件、调用链、结构/指令 | 机制假设与候选 |
| F fixture | 可控模型/镜像、歧义、失配、恢复 | 模型逻辑正确 |
| G 实际游戏 | 受控动作前后变化、功能开关 | 该 build 的已测场景有效 |
| R 重复会话 | 新进程、换局、重连、退出恢复 | 已测生命周期稳定 |
| D 交付 | 从交付目录启动、依赖、配置、包清单 | 已测机器的交付可复现 |

第二案例优先使用 `scripts/fixture_lab.py`（先读 `references/fixture-lab.md`）。它是离线虚拟内存模型，既不附加真实进程，也不证明 native 游戏运行成功。扫描结果和 manifest ground truth 分开使用；不要从答案表抄地址宣称定位能力。

写入路线增加旧字节不符、重复启停、部分失败、恢复冲突、退出和版本失配测试。读取路线增加短读、无效矩阵、旧会话、扫描预算和过期显示测试。

## 6. 更新与交付

1. 按 build hash 存 offsets/signatures/布局与证据。更新后重新走身份 → 候选 → 结构/指令 → 行为 → 回归，保留旧 build 结果。
2. 交付运行所需最小文件、默认配置、使用说明和已测功能表；开发映射、PDB 和验证资料归维护包。记录运行时依赖，CE 探索成功不等于独立程序脱离 CE。
3. 授权、保护构建和商业打包按需接入现有模块；不更改产品隔离标识或把私钥、卡密库写入 skill/客户包。不要为技术试验启动线上发卡或服务部署。
4. 不自动提交或推送。报告最终文件及尚未执行的实际游戏验证。

## 每次任务的交接格式

输出与目标规模匹配的报告，至少包含：

- 目标与输入身份；环境和工具实测能力。
- 技术路线及选择依据；已排除路线与原因。
- 证据表：结论、样本/build、出处、S/F/G/R/D 等级、限制。
- 实现与构建/运行命令；功能状态与恢复策略。
- 验证结果：预期/实际、通过/失败/not_run、日志与复现方式。
- 更新适配记录、交付文件与下一项具体待验证动作。

不要把大量工具输出当结论。给出能复查的关键字节、结构不变量和失败原因；不编造地址、工具连接或实际游戏成功记录。
