# Windows PC 游戏：引擎识别、定位与可恢复实现

适用于单机、离线和自有测试构建的修改器开发。方法覆盖外部读取、数据修改、受控行为补丁与官方/社区 mod 接口；不包含检测规避、驱动和线上作弊。先记录游戏发行渠道、版本、目标功能、进程位数和可复现场景，再选分支；引擎只是路线证据之一，不能直接推出特定偏移可用。

## 先探测能力，再制定调用

检查当前会话技能目录、MCP 工具实际 schema、可用 CLI、目标进程架构。只列出存在的工具；教程中的工具名不等于已接通能力。CLI 可先用 `Get-Command <name> -ErrorAction SilentlyContinue`，再按该工具文档查询版本或帮助；没有可靠 `--version` 的 GUI 工具记录文件版本。工具状态至少分为未安装、存在未试、静态调用通过、动态调用通过、capability_unavailable。

| 能力 | 可选工具 | 最小探测与成功依据 |
|---|---|---|
| PE / 托管识别 | dumpbin、sigcheck、REA 或等价 PE 解析器 | 输出 Machine、PE32/PE32+、CLR directory、导入、节表；保存解析结果与输入哈希 |
| 托管代码 | ILSpy / ilspycmd、dnSpyEx | 对副本导出一个已知类型并找到字段/方法；记录实际版本与导出路径 |
| Native 静态 | Ghidra、IDA、Binary Ninja、ReVa | 项目成功载入正确架构，对一个已知函数返回反汇编、交叉引用；“打开成功”不等于逻辑恢复完成 |
| 运行观察 | Cheat Engine、x64dbg、WinDbg、已有进程读取 MCP | 连接指定测试 PID，读一段已知模块头或已知测试变量并核对长度；断点和写入能力另测 |
| Unity Mono | ILSpy、可用的 Mono 元数据工具 | 枚举真实程序集、类型、字段/方法；运行时域和 JIT 能力需要单独确认 |
| Unity IL2CPP | Cpp2IL、Il2CppDumper、Il2CppInspector 等 | 对匹配的 native 模块和 metadata 运行，记录支持的 Unity/metadata 版本与解析错误 |
| Unreal | 匹配版本的符号、反射/SDK 工具、官方编辑器工具 | 校验引擎版本、对象/名字布局与一个已知对象；禁止套用其他版本固定全局地址 |
| 构建与 UI | 对应 .NET SDK、MSBuild、C++ 工具链、窗口截图工具 | 最小工程编译/启动结果与依赖路径；窗口截图和游戏行为验证分开记录 |

若动态捕获返回 capability_unavailable，继续完成文件静态分析、布局推导和验证计划，明确留下缺口。其他 REA 静态接口成功不能替代动态测量。工作目录与 REA/工具安装目录分别记录；不扫描无关凭据或私有目录来寻找依赖。

## 路线判别

| 路线 | 组合证据 | 容易误判的点 |
|---|---|---|
| Native / 自研 | PE 中缺少目标游戏逻辑 CLR，native 代码、RTTI/vtable/字符串与实体管理结构 | 修改器自身为 .NET，不说明被读取的游戏也是托管引擎 |
| Unity Mono | UnityPlayer、`<Game>_Data/Managed` 下可解析游戏程序集、Mono runtime 文件或模块 | 仅发现 UnityPlayer 不能区分 Mono 与 IL2CPP；残留 Managed 文件也可能是辅助程序集 |
| Unity IL2CPP | GameAssembly 或平台 native 游戏模块，配对 `il2cpp_data/Metadata/global-metadata.dat`，元数据可识别 | 文件名可变；metadata 版本、模块与构建必须对应，反编译 dummy DLL 不是原始 IL 逻辑 |
| Unreal | Engine/Content 布局、pak/utoc/ucas、版本字符串、模块/符号与 UObject 反射迹象 | 单个 UE 字符串或资源扩展名不足以确定版本；shipping/LTO 改变符号与代码形态 |
| 混合或未知 | 启动器、脚本 VM、native 宿主和辅助 CLR 同时存在 | 先定位实际承载所需状态的进程/模块，必要时保留多个候选路线 |

保存证据来源与置信度；至少用文件证据与当前加载模块相互印证。对子进程或重启后的 PID 重新绑定启动时间、架构和模块基址。

## Native：从数据到行为

1. 把功能写成可观察变化，例如测试角色受伤前后生命值、消耗前后资源、移动前后位置。记录数值类型候选、单位、比例和 UI 延迟；未知值先用增/减/不变筛选，候选过多时收窄区域与对象范围。
2. 为候选加入反证：同一场景重复变化、相似实体对照、暂停与加载后重读。区分 UI 缓存、预测值、实际模拟值和存档序列化值；“冻结后数字不动”不足以证明玩法生效。
3. 用可用的访问观察或调试断点确认读写该字段的函数，追踪对象基址和调用上下文。记录 `module + RVA`、结构偏移、数据宽度、对齐和所有者条件；避免把共享函数命中误当成本地玩家专属逻辑。
4. 从符号、字符串交叉引用、RTTI/vtable、容器边界和分配/销毁路径建立对象模型；以两个独立结构不变量验证指针链。不同启动与加载周期重新验证，才将链写入版本描述。
5. 行为修改优先寻找游戏已有配置、脚本、控制台或 mod 扩展点。需要 native 补丁时先理解完整指令与控制流，再进入下述补丁事务；数据与行为定位的证据分别保存。

## Unity Mono：语义优先

1. 确认游戏程序集而非启动器程序集，按玩法名、序列化字段、属性 setter 和事件路径定位状态。记录程序集哈希、完整类型名、字段/方法签名、token 与版本，不仅记录易变 token。
2. 验证对象实例生命周期：单例、组件查找、场景重载、对象池复用与销毁；静态字段不等于固定 native 地址，GC 移动、域重载和 JIT 会使缓存失效。
3. 数据路线验证字段类型、偏移和实例归属；行为路线核对 IL 调用者、setter/更新循环，并在测试构建用插件/受控方法补丁验证。区分源语言签名与实际调用 ABI。
4. 若观察到 AOT native 主体或缺少所需 IL，回到识别阶段切 IL2CPP/native 路线。ILSpy 导出的辅助 DLL 不代表所有逻辑都在 Mono。

## Unity IL2CPP：元数据与机器码配对

1. 保存 native 模块、metadata 的同一构建哈希与 Unity/metadata 版本，使用支持该格式的工具解析；失败记录为格式、配对或工具能力问题，不凭空补全输出。
2. 从 metadata 建立类型、字段和方法候选，映射到 native 方法地址与字段偏移，再在反汇编中核验参数、访问宽度和调用者。dummy DLL 只辅助名称与类型导航。
3. 分清实例字段、静态字段、线程静态、值类型装箱及继承布局；泛型共享、内联、thunk 和 stripped 方法可能让“一个方法名对应一个独立函数”的假设失效。
4. 运行时逐项确认实例归属、场景生命周期、方法是否实际执行。调用测试需核对隐藏参数（如具体版本中的 MethodInfo）、线程附着要求、GC 管理与目标线程；不要凭 C# 签名构造 native 调用。
5. 每次游戏更新重做模块/metadata 配对、布局和方法验证；保留旧映射做差异分析，旧偏移默认失效。

## Unreal：反射帮助建立对象归属

1. 尽量取得匹配构建的符号、引擎版本与公开 mod SDK。确认名字池、对象数组、反射布局的具体版本，读取一个名称和类都可独立核对的测试对象。
2. 按 World → GameInstance/LocalPlayer → Controller/Pawn 或游戏自己的 Subsystem/Component 追踪所需状态。这是候选结构，不是每个游戏固定存在的链。
3. 区分 CDO、蓝图默认值、实例、Actor component 与存档数据；检查对象有效性、类、Outer/World、销毁标记与当前关卡。流式加载、GC 和对象重生时废弃缓存。
4. 利用 UProperty/FProperty、UFunction 参数与函数交叉引用辅助定位；调用 ProcessEvent 需要匹配参数缓冲布局、返回字段和游戏线程条件。反射可见不保证方法适合任意时刻调用。
5. pak/utoc 资源修改和运行时属性/函数补丁分开交付。资源更改在独立副本或 mod 目录中测试，保存原哈希、打包参数与加载验证，避免把资产解析成功写成玩法已改变。

## 共同的受控验证

为每个功能建立一张记录：输入版本/模块哈希、目标行为、基线、触发动作、候选地址或签名、对象归属、预期效果、负面对照、恢复动作、观察日志。先只读验证，再对单变量做最小修改；记录写入前后值和实际行为，不同时开启多个未验证开关。

至少覆盖开启、关闭、重复切换、死亡/重生、读档/新局、进程退出及版本不匹配；按功能选择适用项。重启后重新解析基址，过期对象/epoch 不发布。补丁无法解释的崩溃要保存异常位置和原字节，先恢复基线再缩小实验范围。成功层级明确写为静态定位、只读观测、局部效果、恢复通过或完整回归，不互相代替。

## 可恢复补丁与 ABI

数据写入和代码补丁分别建事务。记录原值或完整原字节、写入长度、定位依据、当前进程身份、保护属性、启用次数和所有权。启用前核对版本、签名唯一命中、完整指令边界和 expected bytes；任一失败返回诊断，不继续猜地址。关闭时确认当前位置仍是本补丁内容，再恢复本事务保存的内容；别覆盖其他修改者的后续变更。释放分配内存前先撤销仍引用它的跳转并确保执行路径已退出。

代码重定位需处理 RIP-relative 寻址、相对 call/jmp、短分支和分支目标；跳转距离影响补丁大小。覆盖若干字节后不能直接拼回原指令而忽略地址变化。修改代码后恢复页保护并刷新指令缓存，验证启用与恢复时序。多线程情况下采用明确的同步/停顿策略，避免一半指令已写另一半未写。

Windows x64 调用核对 RCX/RDX/R8/R9 与浮点 XMM 参数规则、32-byte shadow space、调用点 16-byte 栈对齐、非易失寄存器、flags 与 SIMD 状态保存；x86 则明确 cdecl/stdcall/thiscall 等约定和栈清理方。还需核对结构体返回、异常展开、线程局部状态和引擎线程约束；这些不能由“x64”一个标签推导完毕。

AOB 只屏蔽确属重定位或易变字段的字节，附上上下文与匹配数量；不要把“带通配符”称作自动跨版本兼容。新版本先在副本检查唯一性、反汇编与功能语义，再做受控效果及恢复验证。交付同时提供可关闭路径、故障诊断、版本描述和恢复说明。
